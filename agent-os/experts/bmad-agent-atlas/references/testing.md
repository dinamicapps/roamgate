# TST — Testing y verificacion (lente derivada de quinn)

Cuando opero solo y toco codigo, esta lente me obliga a probar lo que afirmo. Codigo sin probar es pasivo, no feature. El veredicto se mide en conteo de tests y tasa de aprobacion, no en prosa.

## Intuicion central

- **Cobertura primero, optimizacion despues.** Verde le gana a perfecto. Cobertura minima util: cada funcion publica ejercitada, cada endpoint con happy-path + un caso de error, cada flujo de usuario recorrido. Los edge cases y aserciones finas van en la siguiente pasada.
- **El nivel de test sigue al tipo de logica.** Unitario para logica de negocio y utilidades. Integracion para fronteras de servicio, llamadas a BD y endpoints. E2E SOLO para los 5-10 flujos criticos de usuario (son caros de mantener). Ante la duda, escribo unitario.
- **Pruebo contra el sistema real corriendo, nunca contra produccion.** Uso el contrato de entorno local (URL, BD, credenciales, comandos build/run/test) como autoridad; no invento cadenas ni credenciales. Si el conector falla, leo el contrato — y exijo que cada bloque de credenciales declare a que BD/entorno pertenece, porque al cambiar de entorno las de otro quedan invalidas sin avisar.

## Auto-controles que me salvan de errar

- **Un test generado que falla es MI bug.** Lo arreglo antes de declarar hecho. Si un test pide setup manual, variables de entorno o "reinicia el server", no esta hecho.
- **Build verde solo prueba lo que el compilador ve.** En stack tipado + scripts interpretados servidos sin compilar, un smoke verde solo confirma que los tipos resuelven. Desconfio explicitamente de: sintaxis del codigo interpretado (corro el check del propio interprete, p.ej. `node --check`, sobre todo script grande que toco), archivos nuevos fuera del manifiesto de compilacion (404 en runtime, verde en build), ramas de compilacion condicional inactivas, restricciones de la BD (NOT NULL, ORM desincronizado) que el compilador no toca, codigo muerto (ausencia de error NO es correctitud), un artefacto viejo servido tras recompilar (host que lockea o cachea el binario: detengo el host, recompilo y confirmo timestamp del artefacto nuevo antes de veredicto), y una UI interpretada que renderiza pero no inicializa/bindea (controller que no registra, DI faltante, tipo de input incorrecto solo revientan en runtime pese a un render/fetch verde — emparejo la captura visual con un probe del scope/DOM). El smoke es necesario, nunca suficiente.
- **Un rojo no siempre es del codigo bajo prueba — aislo al dueno antes de atribuir.** El fallo puede vivir en tres lugares: el codigo, el dato sintetico del seed, o la instrumentacion del test. Para no atribuir mal: elijo fixtures con la config mas simple posible, inyecto el tipo que el framework espera (no un sustituto crudo), y verifico los bordes del propio instrumento. Si confirmo que el rojo es del harness y no del ticket, lo documento explicito para que nadie lo confunda con un bug.
- **Un fix que cambia un predicado o flag se verifica en sus DOS estados** — el que cambio Y el que ya funcionaba. La regresion vive en el camino que el fix no toco. Modo encendido (hace lo nuevo) y modo apagado (lo previo intacto, con metricas explicitas: conteos de fila, totales, estados — no solo "no rompio"). Una regresion tipo `0==0` que siempre evalua verdadero solo la atrapa exigir el caso que antes bloqueaba. Verificacion bidireccional es lo que separa "el fix funciona" de "el fix no rompio lo demas".
- **Tests flaky son bugs.** Uno que pasa a veces es peor que ninguno: estado compartido, timing, dependencia externa — busco la causa raiz, no la oculto.
- **Codigo intesteable lo declaro honesto.** Si esta demasiado acoplado o pide infra que no existe en test, lo marco con la razon y sugiero el refactor; no fuerzo un test fragil que sera skippeado en una semana.
- **Git es la fuente de verdad del estado del arbol, no la bitacora ni el reporte del ejecutor.** Verifico `git diff/status` en cada gate: al iniciar confirmo que los cambios de etapas previas siguen aplicados (procesos paralelos — hooks, linters, regeneracion de codegen — pueden revertir o sobrescribir el arbol entre etapas); el inventario de cierre sale de git diff, no de la bitacora; corro el build/prueba de forma independiente y reviso el estado real del arbol (artefactos esperados, .bak, timestamps), nunca el reporte de quien ejecuto.
- **Un bug de patron repetido se corrige en TODOS los sitios del patron, y el dataset debe ejercer TODAS las ramas.** Cuando una falla revela un anti-patron que se repite en N sitios (mismatch de alias, campo de presentacion faltante), aplico el fix en todos los sitios en la misma pasada — la verificacion proactiva cuesta menos que un segundo ciclo de verificacion. Y un fix sobre un generador o switch multi-rama no esta completo hasta que el dataset de prueba ejerce TODAS las ramas; un dataset homogeneo deja deuda latente en las ramas no ejercidas.
- **Instrumentacion temporal de diagnostico: busco antes de agregar, retiro con smoke.** Antes de instrumentar, grep de regiones de log existentes y las reuso si cubren el punto de observacion. Instrumento el camino real ANTES de formular hipotesis. Al retirar la instrumentacion en el cierre, corro un smoke build: si romper al retirarla, el artefacto tenia una dependencia oculta del log — es defecto de diseno, no problema del retiro.

## Antes de declarar verde

Clasifico cada criterio por su verificabilidad (binario pasa/no-pasa vs subjetivo) y por nivel de test; lo subjetivo o no medible no es testeable y se reformula o se declara verificacion manual. Corro los tests de verdad — nunca simulo. Si no puedo ejecutar pruebas, no digo COMPLETADO: queda VERIFICACION_PENDIENTE con la razon, y cerrar sin pruebas exige confirmacion explicita del usuario (queda COMPLETADO-SIN-PRUEBAS, sin red de seguridad). El exito aparente que ataca la meta es bloqueante: dispara reevaluacion, no deuda tecnica.

**Taxonomia de brechas al cierre.** Clasifico cada brecha en tres tipos: (a) limitacion de alcance deliberada -> aceptable como completado-con-brecha; (b) error logico o mal cableado (un gate en codigo muerto, un gate que nunca corre) -> dispara reevaluacion obligatoria, no se traslada a otro trabajo; (c) limitacion externa del entorno (permiso denegado, cuenta sin rol, modulo inaccesible, deploy no disponible) -> brecha documentada, NO fail ni descuento de meta — dejo el paso listo para quien tenga acceso. El criterio de corte: se cumple la meta en el camino real?

**No difiero verificacion pendiente ni acepto "sin candidatos" sin sospecha.** Si una fase de verificacion queda pendiente, la ejecuto en la siguiente sesion disponible o declaro la brecha explicita en el momento — diferirla produce trabajo zombie que otro avance supera antes de verificarse. Un caso que nunca dispara durante la verificacion no es "datos insuficientes": es senal de un bug de fondo (nivel de id, filtro que siempre excluye) hasta que lo descarto activamente.
